# FastOffload完整消融实验方案：排除CPU累积与CPU归约

## 1. 文档状态与实验范围

本文固化当前讨论确定的完整消融方案，覆盖方法设计、选择性计算、GPU通信、
CPU↔GPU传输、异步更新、B优化器放置、参数敏感性和正确性验证。

**当前状态：仅制定方案，未据此启动训练、分配实验编号或填写测量结果。**
算法质量实验仍保持暂停，待单独授权。本文不会恢复已经停止或取消的实验队列。

### 1.1 已明确排除的配置

- 不测试GPU归约＋CPU累积B。
- 不测试CPU归约＋CPU累积B。
- 不删除已有CPU路线代码、历史结果或失败记录。
- 凡需要B跨步累积，均在GPU进行；M3故意取消B跨步累积，不引入CPU累积。
- B优化器放置只比较CPU更新与GPU更新，梯度归约和累积位置保持GPU。

### 1.2 技术贡献的表述边界

这里的“FastOffload提出的”，指当前实现中与对照路径不同的设计组合，
不宣称所有组成技术都由FastOffload首次提出。

ZeRO分片、Adam、pinned memory、CUDA stream、event、Reduce-Scatter和All-Gather
均不是FastOffload独有技术。需要验证的是它们如何与A/B/C选择、owner布局、
低频更新和版本化发布结合，产生实际收益。

### 1.3 三种不同的消融

| 类别 | 改变什么 | 主要评价 |
|---|---|---|
| 方法消融 | 重要性排序、更新频率、梯度使用方式 | 质量与训练成本 |
| 系统消融 | 计算、通信布局、传输或执行方式 | 吞吐、显存、通信与等待 |
| 放置/调度消融 | optimizer设备、完成与发布时机 | 速度、状态内存和陈旧性 |

系统消融应尽量保持更新数学，但当前实现按ready状态发布参数，
执行速度变化本身可能改变后续forward使用的版本。因此需要记录真实发布时序，
不能自动宣称所有系统变体的完整训练轨迹逐位相同。

**不得通过关闭必要的event、版本保护、overflow检查或collective顺序约束来提速。**
错误结果不能作为性能数据。

### 1.4 实现与启动前置条件

- 本文中的实验编号不是现有配置字段，不能直接作为可运行开关。
- 大部分负对照、细粒度计时和L1的GPU B更新路径仍需实现并验收。
- 新开关关闭时必须保持F0行为，不顺带重构生产路径。
- 先做固定梯度重放、CPU测试和分布式门控，再考虑真实模型性能测试。
- 本文不授权实现全部变体、修改训练代码或启动实验。

## 2. 统一完整配置F0

所有系统消融使用同一份冻结源码和同轮F0作为分母，不混用历史最快结果。

| 项目 | F0配置 |
|---|---|
| 模型 / 数据 | Qwen2.5-7B-Instruct / Alpaca |
| 并行 / 精度 | 双卡、BF16、ZeRO-2 CPU optimizer offload |
| 每卡microbatch / GAS | 1 / 1 |
| seed / 数据起点 | 42 / epoch 0，固定实际样本顺序 |
| 输入处理 | cutoff 512，response-only labels，padding到8的倍数，不packing |
| 模型设置 | activation checkpointing开启，`use_cache=false` |
| 优化器 | AdamW，恒定LR 5e-6，betas=(0.9, 0.95)，eps=1e-8，weight decay=0.1 |
| 梯度裁剪 | clip=1，无LR scheduler |
| 重要性预热 | 一次Native预热 |
| 重要性评分 | 输入列的`abs(current-reference).sum(dim=0)` |
| A/B比例 | 受支持二维参数中，各约10%，按实际列数取整 |
| A | 每个成功步骤在owner GPU更新 |
| B | GPU归约、GPU累积，周期4取mean，owner CPU更新 |
| C | 当前边界梯度，周期4，owner CPU更新 |
| 普通步backward | Packed selective backward；不支持的路径保留合法fallback |
| 密集边界 | 完整backward、Native梯度归约 |
| 普通步梯度通信 | owner-aware选中元素归约 |
| 更新值发布 | 只发布本次更新的A或B/C |
| CPU输入与返回 | 大owner路径使用BF16 shared+pinned槽/镜像 |
| Adam状态 | FP32 master、m、v |
| 异步容量 | `max_async_lag=2` |
| 压缩桶目标 | `compressed_bucket_bytes=134217728`，即128 MiB |
| B路由 | 显式设置`accumulation_device=gpu`、`second_reduce_scatter_device=gpu` |

非二维参数保持当前dense处理方式，不套用A/B列比例。
A的GPU间更新值发布可能使用FP32，不能把所有通信统一记为BF16。

固定模型初始状态、输入顺序、优化器参数、clipping、模型设置、GPU映射和既有CPU线程配置。
不额外修改allocator、线程数或NUMA策略来帮助某个变体。
启动前再核验GPU资源和软件环境，不能从历史记录推断当前GPU空闲。

“每个成功步骤”不包含overflow步骤。B周期包含普通步和当前边界步，
C不跨Hybrid步骤累积。Forward和输入梯度传播保持dense。

## 3. 方法设计消融：为什么需要A/B/C

本组主要评价质量—成本取舍，不是纯性能消融。

| 编号 | 变体 | 具体变化 | 验证目标 |
|---|---|---|---|
| M1 | 随机列选择 | 每层A/B数量不变，随机分配列 | 重要性排序是否优于随机 |
| M2 | 交换A/B排序区间 | 原高排名列进入B，次高排名列进入A | 高频更新是否应分配给更重要的列 |
| M3 | B不做跨步累积 | B只使用当前边界梯度，仍周期更新 | B跨步累积是否必要 |
| M4 | A也周期更新 | A仍在GPU，周期内累积取mean后更新 | A每步更新是否必要 |
| M5 | 不更新C | 保留C梯度计算与统一数值检查，但不执行C参数更新 | 密集边界C更新是否必要 |

### 3.1 约束与混杂因素

- M1/M2固定选择数量和随机种子，但可能改变owner分布与padding。
  必须记录实际owner元素数和通信字节，不能把吞吐变化全部解释为排序质量。
- M3改变的是GPU上的B跨步累积语义，不是关闭CPU累积。
- M4中A的optimizer更新次数随周期变化；不能用零梯度调用Adam代替跳过更新，
  否则动量和weight decay仍可能改变参数。
- M5保留C参与本步全局数值检查和clipping，仅跳过C参数及optimizer状态更新。
  不能把梯度设为零但继续执行Adam当成“不更新C”。
- M5只是算法负对照，不能取代正式Hybrid A/B/C，也不能作为同等质量加速的直接证据。
- 所有方法变体都需要单独定义状态、计数、版本与checkpoint语义，并先验证。

### 3.2 建议质量预算

**本组仍暂停；以下是待授权方案。**

- F0及M1—M5各1024步，固定实际输入顺序和token预算。
- 在初始状态及256、512、768、1024步进行验证。
- 使用固定验证集，不使用测试集调参。
- 验证采用响应token加权NLL，报告训练曲线、验证曲线和总时间。
- 使用普通评估路径，不能让选择性训练hook改变验证计算。
- 只有配置确实达到共同质量阈值，才计算time-to-quality。
- 单seed结果不宣称统计显著性，也不把短预算NLL等同于最终下游能力。

## 4. 计算与GPU通信消融

### 4.1 S1：关闭Packed Selective Backward

```text
F0：直接计算A+B的dW
S1：计算完整dW，再提取A+B
```

其余选择、归约、更新方式不变。

观察普通步dW时间、端到端吞吐、临时梯度显存、packed适用参数比例及fallback次数。
记录普通步与密集边界分别占多少时间，避免将普通步kernel收益直接等同于总吞吐收益。

已有历史结果约为163.48对156.60 input tokens/s，提升约4.39%。
这只证明该历史配方下packed backward的净收益，不证明通信压缩的独立收益。
新实验必须使用同源F0，不能直接使用历史数字作为分母。

### 4.2 S2：关闭梯度载荷压缩

```text
F0：归约载荷只包含选中A/B元素
S2：把同一组A/B梯度展开到dense布局，其他位置填零，再归约
```

约束：

- 保留packed backward，不新增有效C梯度或C更新。
- 保持逻辑参数顺序、owner划分和数值平均规则。
- 按桶或有界子块展开，不建立额外全模型GPU暂存。
- 归约后仍只消费A/B，已有密集边界行为不变。
- 记录dense展开引起的实际分桶变化，不假定调用次数一定相同。

观察有效元素、padding、零占位、实际载荷、打包/展开/归约时间。
本项测量压缩布局整个路径的净收益，不是只测网络字节差。

### 4.3 S3：关闭直接归约到owner

```text
F0：选中梯度Reduce-Scatter → owner结果
S3：选中梯度All-Reduce → 每卡完整选中结果 → 提取owner部分
```

保持A/B选择、owner optimizer状态分片、梯度平均和clipping规则不变。
使用有界bucket，不同时在GPU保存全模型梯度。

验证直接产生owner-local梯度，是否优于先获得完整选中梯度再截取。
这不是验证ZeRO分片本身，而是验证选中梯度与owner布局的直接结合。
归约算子变化可能改变浮点归约顺序，使用数值参考与合理误差检查，而非强求跨路径逐位相同。

### 4.4 S4：关闭GPU更新值的选择性发布

```text
F0：GPU间只发布本次更新的A或B/C
S4：发布较宽布局，包含未更新位置，但只应用有效更新值
```

CPU↔GPU返回保持F0。未更新位置不能覆盖模型参数。
按桶处理，不建立额外全模型GPU staging，并保留版本顺序与forward可见性。

验证选择性参数发布的通信与暂存收益。
该对照只扩展发布载荷，不声称完全复刻Native的完整运行流程。

### 4.5 S12：计算压缩与通信压缩的交互

S12是S1与S2的组合编号，不表示还有未列出的S5—S11。

| Packed backward | 梯度载荷压缩 | 配置 |
|---|---|---|
| 开 | 开 | F0 |
| 关 | 开 | S1 |
| 开 | 关 | S2 |
| 关 | 关 | S12 |

验证两项收益是否相互独立，或者关闭其中一项后另一项被瓶颈遮蔽。
不能简单相加S1、S2的百分比收益。

## 5. CPU↔GPU与异步执行消融

### 5.1 T1：最终梯度改为FP32传输

```text
F0：BF16跨PCIe → CPU侧转FP32
T1：相同量化后的梯度扩成FP32跨PCIe
```

为隔离传输链路而非优化器精度：

1. 两组先得到相同BF16数值。
2. T1只在传输段扩成FP32。
3. 到CPU后恢复与F0一致的最终槽和mean处理顺序。
4. CPUAdam仍使用FP32 master、moments与梯度工作区。

临时空间必须分块有界。T1保留F0的CPU低精度槽内处理顺序，
不能顺带把B的mean改为FP32，否则同时改变数值计算。

验证低精度最终梯度传输链路的净收益。
额外转换与复制开销必须报告，不能把全部差异归为纯PCIe带宽。
此对照不是Native完整路径的复刻。

### 5.2 T2：CPU返回包含未更新位置

```text
F0：CPU只返回owner B/C更新值
T2：返回包含A占位的较宽布局，再提取B/C
```

A占位不写入模型，不能覆盖GPU最新A。
GPU间发布仍使用F0，以免同时改变H2D和GPU间通信。
分块传输，不引入额外完整GPU staging，不要求CPU重新维护A的Adam状态。

验证只返回B/C的H2D收益；记录CPU布局构造和提取成本。
该路径是受控的载荷负对照，不宣称等同于Native参数回传。

### 5.3 T3：C下传逐片等待

每片C提交D2H后，训练线程立即等待，再推进后续工作。
保留逐片直写最终CPU槽，不先将整个C留在GPU。

验证C提前异步下传与后续backward重叠的实际收益。
“逐片等待”不意味着此前已经排队的所有GPU活动都不可能重叠，
应通过时间线确认实际执行，不能仅凭开关名称宣称零重叠。

### 5.4 T4：B下传立即等待

边界B累计和提交D2H后，训练线程立即等待event。
B仍在GPU跨步累积，仍只在边界下传。

验证后台传输等待实际隐藏了多少时间。
当前前向准备存在GPU同步，本项可能收益很小；小收益也是有效结果。

### 5.5 T5：参数H2D逐次等待

每次B/C返回复制完成后，再继续提交后续发布操作。
保持相同返回值、dtype、分桶及版本安全保护。

验证当前nonblocking H2D是否缩短发布过程。
F0的H2D与后续发布使用调用时的当前stream，并非已经完成独立H2D预取流水线。

### 5.6 T6：传输全部同步化

组合T3、T4、T5，但CPUAdam仍保持后台执行。
验证传输异步化整体净收益，不能直接相加三个单项收益。

### 5.7 T7：CPU更新改为边界串行完成

边界提交后，按合法版本顺序等待CPU更新并发布完成，再进入后续训练。
不能直接设置未支持的`lag=0`，不能绕过输入槽、返回镜像和发布协议。
若存在更早版本，必须按顺序推进，避免等待一个依赖旧版本发布的任务而死锁。

验证CPU更新与后续GPU计算重叠的价值。
此变体改变更新生效时机，属于调度消融，不宣称与F0训练轨迹完全相同。

### 5.8 本组的解释边界

验证的是面向A/B/C的传输范围、精度位置与异步组织方式，
不是声称nonblocking、copy stream或后台CPU进程本身由FastOffload发明。

当前实现仍有C传输收尾等待、边界A发布后的GPU同步、pending任务下的前向准备同步，
以及容量反压和最终drain。保留这些非目标同步点，不能顺带删除后声称只测了一个因素。

## 6. B优化器放置消融

本组只有两个配置；B始终在GPU归约和累积。
本版将“B改GPU更新”统一编号为L1，替代早期讨论中的L3。

| 配置 | B归约 | B累积 | B更新 |
|---|---|---|---|
| F0 | GPU | GPU | CPU |
| L1 | GPU | GPU | GPU |

### 6.1 L1保持的语义

- B仍每4个成功步骤更新，不能直接变成每步更新的A。
- 累积包含普通步和当前边界步，仍取mean。
- 保持相同的提交LR规则与FP32 master、m、v。
- 先确定量化与mean顺序是否与F0一致；若不同，必须明确标为额外数值差异。
- 尽量保持B/C同版本发布；若B提前算好，在GPU保留待发布结果，不能立即改模型绕过版本协议。
- 记录真实更新完成、发布与首次使用位置；CPU工作量变化仍可能改变共同ready时机。
- 输入冻结、结果保护、overflow、恢复与drain需要新的对应验证。

### 6.2 测量指标

| 指标 | 用途 |
|---|---|
| 吞吐、完整循环＋drain | GPU更新B是否真正更快 |
| GPU allocated/reserved峰值 | 额外显存代价 |
| B的FP32 master/m/v占用 | 明确状态成本 |
| 边界GPU更新时间与临时空间 | 是否挤占计算与显存带宽 |
| B D2H/H2D字节 | 避免了多少CPU往返 |
| CPUAdam时间 | 减少了多少CPU工作 |
| 待发布GPU结果与版本时序 | 延迟发布是否引入额外存储与等待 |

FP32 master、m、v合计约12字节/owner B元素，
但不能把这个静态数直接当作L1相对F0的实测峰值增量：
B双buffer、传输槽、临时工作区和待发布结果的生命周期也可能变化。

结论应描述给定显存预算下的速度—内存取舍，不预设CPU更新B一定最优。

## 7. 参数敏感性与适用范围

采用单因素变化，不做所有参数的笛卡尔积。

| 参数 | 建议取值 | 验证目标 |
|---|---|---|
| B/C周期 | 1、2、4、8 | 更新频率、传输量、质量取舍 |
| A/B选择比例 | 各5%、10%、20% | 覆盖率、计算和状态成本 |
| max async lag | 1、2、4 | 延迟隐藏、buffer内存与陈旧性 |
| 桶目标 | 64、128、256 MiB | 通信次数、padding、暂存与吞吐 |
| 工作负载 | Alpaca、GSM8K、XSum | 计算/通信占比变化后的收益 |
| GPU数量 | 2、4、8，按资源授权 | owner粒度与通信扩展性 |

约束：

- 本轮所有路线保持GPU归约；需要B累积时保持GPU累积。
- 当前配置将A/B比例绑定，不把独立调整两者说成已有功能。
- 周期、比例、lag会影响训练轨迹；最优质量结论需要相应质量实验。
- lag是版本容量，不是并行CPUAdam数量；大owner路径只有一个CPUAdam进程和一个返回镜像。
- bucket目标不是严格显存上限，单参数和owner padding可能超过目标。
- 不同数据集不是纯序列长度消融；若研究长度，需另固定内容和标签预算。
- 多GPU实验需固定全局输入token预算和解释有效batch变化，不能直接套用双卡速度比分母。
- 资源不足或OOM如实记录，不自动替换模型、改allocator或改变配方。

建议跨工作负载先扩展F0、S1、S2、T6、L1，不立即复制整个矩阵。
历史64/128/256 MiB结果保留，小幅差异不能称为统计最优。

## 8. 初始化与内存生命周期验证

### 8.1 初始化成本

单独测量：

- CPU reference保存时间及内存。
- 分块评分时间与峰值工作区。
- `comparison_chunk_rows`变化的影响。
- reference逐参数释放及最终清空。
- Native Adam状态迁移到Hybrid状态的时间与内存。

这些结果单独报告，不混入稳态吞吐。
分块计算属于工程实现，不单独包装成独创算法。
不要用额外全模型GPU FP32副本作默认负对照。

### 8.2 内存账本

至少区分：

1. 本地未归约A/B梯度。
2. owner当前步梯度。
3. B双累积buffer。
4. GPU A optimizer状态。
5. L1额外GPU B optimizer状态及待发布结果。
6. 通信打包、padding与归约输出。
7. CPU版本输入槽、FP32梯度工作区和返回镜像。
8. CPU optimizer master与moments。

不能把清零、逻辑释放、删除引用与实际allocated释放混为一谈。
FREE但保留分配的buffer仍占内存；多个bucket输出可以同时存活。

无需恢复旧版额外全模型GPU暂存来证明改善，优先采用张量生命周期账本与有界对照。
如记录CPU内存，区分RSS、PSS、已知live pinned字节与累计注册/分配字节；
未测项目留空，不把RSS相加当作PSS。

## 9. 正确性验证矩阵

采用单元测试、分布式门控和延迟/故障注入，不关闭安全保护跑性能。

| 机制 | 验证方式 |
|---|---|
| 确定性collective顺序 | rank缺失梯度、owner空片段、不同本地执行速度 |
| 版本专属输入槽 | 延迟CPU任务，检查槽不会被提前覆盖 |
| B冻结buffer保护 | 延迟D2H，检查后续累积不会污染旧版本 |
| 返回镜像保护 | 延迟H2D，检查CPU不会提前覆盖 |
| forward可见性 | 延迟发布，检查forward不会读未完成参数 |
| overflow | 当前无效步不更新，历史有效B和有效任务保留 |
| LR归属 | 排队任务使用提交时LR，包含零LR |
| Checkpoint/关闭drain | pending清零、状态一致、worker退出 |
| 新消融路径 | 固定梯度重放，对照数值参考检查更新规则 |

算法或调度发生变化时，不强求不同配置最终模型逐位一致；
但每个配置内部的GPU参数副本必须一致。

对系统变体优先用固定梯度重放检查局部数学，再用真实模型检查完整生命周期。
归约顺序或计算设备变化引起的误差需按参考值制定容差，不能任意放宽以掩盖错误。

大模型optimizer恢复、已运行CPUAdam回滚等尚未验证能力，不能写成已支持。
当前overflow验证只承诺当前无效步不提交、之前有效累积和任务保留。

## 10. 统一测量与验收

### 10.1 第一轮系统预算

每配置：

- 正确性门控：36步，前20步为测量warmup。
- 性能测试：200步，前40步为测量warmup。
- 一个seed、一次性能尝试。
- 门控不是性能重复，也不纳入性能均值。

测量warmup与算法最开始的一次Native重要性预热是两个概念。
这是系统筛查预算，不足以宣称多seed统计显著性。
长预算、重复实验或质量测试需另行确认，不因结果不理想自动重试。

F0也必须在本轮同一源码和runner下测量。
冻结计划顺序并记录每次时间与资源观察，避免事后选择最有利窗口。

### 10.2 端到端指标

```text
吞吐 = 所有rank实际非padding输入tokens / 所有rank中最大的测量窗口耗时
```

同时记录：

- padded tokens、nonpadding input tokens、supervised tokens和样本数。
- 普通步与密集边界host耗时分布。
- 测量窗口吞吐、窗口后尾部与drain开销。
- 完整训练循环＋最终drain时间。
- GPU allocated/reserved峰值，使用相同reset边界。

窗口可以从有pending任务时开始或结束，不能隐藏这一事实。
完整循环包括预热，不包括engine初始化、结束后的全量审计和teardown；这些成本另外记录。
GPU allocator峰值在engine初始化后重置，并包括训练预热，不等同于冷启动NVML峰值。
Host-step时间不是同步GPU kernel时间。

### 10.3 分阶段指标

- dW计算，packed适用范围和fallback计数。
- 梯度提取、打包、展开、归约。
- 有效元素、padding、实际通信载荷。
- D2H/H2D字节、复制次数及event区间。
- CPUAdam排队与执行。
- GPU更新值All-Gather、scatter与完整发布时间。
- 前向准备GPU同步、共同ready检查。
- 队列反压、返回镜像复用等待、最终drain。

后台等待时间不等于关键路径损失时间；重叠阶段不能相加。
CUDA event区间可能含依赖等待，不直接等于纯PCIe链路占用。
不能把GPU间通信字节与CPU↔GPU字节混算。

细粒度计时需要新增instrumentation，不能假定现有计数器覆盖完整路径。
正式测试使用所有配置一致的轻量计数与延迟读取方式，不为每个计时点额外同步GPU。
重型profiler放在独立诊断门控，不污染正式吞吐分母。

### 10.4 版本时序

对每个B/C版本记录：

```text
提交step → 更新完成 → 发布step → 首个使用该版本的forward
```

当前按ready发布，执行速度变化可能改变参数生效位置。
必须记录实际时序，不能只看更新总次数。
若后续需要严格固定发布时机的研究，应另设计配套对照，不能默默改变F0生产调度。

### 10.5 验收条件

- 同组实际输入、mask与配置差异符合预先定义。
- 算法不变的消融，梯度使用、有效更新次数与LR归属符合预期。
- 实际通信量、dtype、设备和buffer生命周期与声明路径相符。
- GPU完整模型副本一致，版本顺序合法。
- 最终pending为0，worker和注册buffer正常清理。
- 对于尾部不足一个周期的B，不虚构一次C更新来清空。
- 失败、中止、OOM保留，不拼接、不补造指标。
- 外部争用只观察记录，不自动停训练、重试或干预他人进程。
- 观察失败或查询报错只记录，不自动成为训练终止条件。
- 用户明确要求停止时，只处理已核实归属的任务，并先停止会继续发起实验的监督队列。

## 12. 结果组织、历史数据与归档

### 12.1 四张主结果表

1. 系统消融表：吞吐、GPU显存、完整循环＋drain。
2. 通信归因表：有效字节、padding、D2H/H2D、同步与反压等待。
3. B放置取舍表：CPU更新B与GPU更新B。
4. 方法质量表：M1—M5的NLL、成本、质量曲线。

每个系统对比使用同轮F0，报告绝对值与相对变化，不仅给百分比。
组合消融报告组合净收益，不将单项收益相加。

### 12.2 Native与ZenFlow的角色

Native、ZenFlow属于外部基线对比，不计入上述14个FastOffload系统配置。
如果补充外部基线，需要冻结各自真实配方，明确Native GAS=1、ZenFlow GAS=4等差异，
不能宣称与FastOffload拥有相同更新数学。

S2、S4、T1、T2是受控负对照，不是完整Native或ZenFlow复现。
安全地扩大通信载荷只用于单因素研究，不替换生产路径。

### 12.3 历史结果的使用边界

- 已有packed backward和桶大小结果保留为历史证据，不混作新源码分母。
- CPU累积、CPU归约路线不进入本轮矩阵。
- 此前中止的CPU路线200步结果仍是中止，取消的排队任务仍是未运行。
- 不恢复旧队列，不删除历史实现、输出或失败日志。
- 现有吞吐结果不能反推各项PCIe同步等待已经减少了多少。

### 12.4 新实验归档要求

如后续获准执行，建立新的冻结实验目录，保存：

- 计划与配置差异、实验顺序。
- 源码快照、HEAD、未提交diff、runner和原生编译输入的hash。
- 模型与数据来源、样本ID及实际token计数。
- 路径审计、更新审计、版本时序、资源观察。
- 门控、正式性能、诊断profile的独立状态。
- 最终验收、worker/进程清理和drain记录。

不能把诊断profile或门控当作性能重复。
若更新实验工作簿，先备份、串行写入，尚未验收的指标留空。
不修改冻结历史runner，不发布模型、私有会话或无关实验资产。

## 14. 最终结论应回答的问题

1. 重要性排序、A高频更新、B跨步累积、C边界更新分别是否必要？
2. 选择性dW计算、选中梯度归约和选择性参数发布分别贡献多少？
3. 低精度最终梯度传输与异步执行减少了多少端到端成本，而不只是后台等待？
4. GPU显存足够时，B是否应改为GPU低频更新？
5. 收益在不同周期、比例、桶大小、工作负载与GPU数量下是否仍成立？

主线是区分“算法少做了什么”“实现把什么做得更高效”和“当前硬件下选择了什么取舍”。
所有需要B累积的FastOffload变体都保持GPU累积，本方案不包含CPU累积实验。
